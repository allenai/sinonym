# Sinonym Data Directory

This directory contains the data files and trained models used by the Sinonym library.

## Data Files

### Conservative East Asian name-order lexicons

- **`east_asian_roman_lexicons.json.gz`**: sorted Romanized Japanese directional
  and possible-surname keys, reviewed exact given-first surfaces, Japanese
  given-name keys, and Korean and Vietnamese surname keys. Possible surnames can
  veto a selected flip but cannot initiate one; conflicting directional
  evidence requires supporting paper context.
- **`japanese_native_lexicons.json.gz`**: sorted Japanese native-script surname
  and given-name forms used to score compact-name boundaries.

These assets are primarily component lexicons. The Roman asset also contains a
small reviewed set of exact given-first Japanese surfaces. They are generated
deterministically from hash-pinned MIT and CC0 sources; see
[`EAST_ASIAN_NAME_LEXICONS.md`](EAST_ASIAN_NAME_LEXICONS.md) for attribution,
the exact-surface policy, and the regeneration command.

### Name Frequency Data
- **`familyname_orcid.csv`**: Chinese surnames with frequency data (parts per million) derived from ORCID records. Contains the most common Chinese surnames like 王, 李, 张, etc., with their frequency statistics.
- **`givenname_orcid.csv`**: Chinese given name characters with usage statistics from ORCID records. Includes character, pinyin romanization, and frequency (ppm).

### Corpus-Derived Given-Name Statistics
- **`given_position.csv`**: Per-syllable counts of romanized syllables in the first (`initial_count`) and second (`final_count`) position of two-syllable Chinese given names. Consumed by the positional feature for 3-token parses (`NameParsingService`, deadband 1.5 / cap 1.5).

It is generated by `scripts/generate_name_statistics.py` from two sources pooled together (per-row provenance in the `source` column):
1. **wainshine/Chinese-Names-Corpus 120W** (Apache-2.0, ~1.14M Han full names; download command in the generator docstring — the 12MB raw corpus is not committed). Names are split deterministically against the `familyname_orcid.csv` surname inventory (98.9% split rate) and romanized per character with pypinyin; 963,777 two-syllable given pairs.
2. **In-house byline supplement**: 247,690 distinct two-token romanized author names with exactly one hyphenated token, mined from an author-mention parquet via the hyphen convention (the hyphenated token is the given name). Distinct-name weighted and rescaled to the 120W pair total before pooling, so it both covers non-pinyin spellings ("kung", "sang" as a given initial) and keeps byline conventions alive for syllables rare in the Han corpus.

Thresholds: byline-only positional rows need >= 10 distinct names. This keeps the asset small (given_position.csv ~10KB).

Training-data provenance: this asset is trained on the 120W corpus plus byline mining only. `acl_2025_authors.txt` is **not** a training source for it (it remains eval provenance via `tests/test_acl.py`); neither source uses sinonym's own parser output as labels (only surname-inventory membership and the hyphen orthographic convention), so there is no train/eval circularity.

Attribution: the 120W corpus is from [wainshine/Chinese-Names-Corpus](https://github.com/wainshine/Chinese-Names-Corpus), Apache License 2.0.

### Romanization-Conditional Surname Table
- **`surname_romanizations.csv`**: Per-spelling surname shares keyed by as-written (norm_light) romanized spelling. Generated by `scripts/generate_surname_romanizations.py` from the repo's own romanization rule tables; consumed by the surname-scoring discount in `NameParsingService`.
  - `spelling`: as-written romanized spelling (lowercase, diacritics/hyphens stripped — a `norm_light` fixed point).
  - `mandarin_target`: the Mandarin pinyin surname whose frequency mass the spelling reaches through romanization remapping (or through the `CANTONESE_SURNAMES` alias).
  - `surname_ppm_as_written`: estimated surname frequency (ppm) the spelling carries *as written*: the full target mass for attested romanizations, `target mass x target_share` for penalty spellings.
  - `target_share`: share of the remap target's surname mass the spelling keeps when scored as a surname. `1.0` for attested surname romanizations (`CANTONESE_SURNAMES` keys, curated Wade-Giles/Taiwanese surname spellings such as `tsai`, `kuo`, `hsieh`); `~e^-4` (the measured operating point) for spellings that inherit surname mass only via remapping with zero as-written attestation (e.g. `fai` -> `hui`, `kung` -> `gong`).
  - **Korean-dominant full-share exclusions** (`KOREAN_DOMINANT_FULL_SHARE_EXCLUSIONS` in the generator): five `CANTONESE_SURNAMES` keys whose as-written spelling is overwhelmingly Korean — `jung` (정), `moon` (문), `im` (임), `kyeong` (경), `pak` (박) — are demoted from full share to the penalty share. Granting them their Mandarin target's full mass (zheng/wen/lin/jing/bai) over-credited Korean surname-first names in routing (net -pp_vys on cases like "Jung Im Na"/"Jung Mi Cha"/"Pak Siau Wei"). They stay attested as-written but score at the discounted mass (a rare Chinese surname) rather than the full target. Their real-but-minor Chinese usage keeps the penalty share instead of falling to nothing. Heavily Chinese-used overlap spellings stay full share (`lee` 李, `lim` 林, `chang`/`jang` 张, `choi` 蔡, `ho` 何, `han` 韩, `yu` 于/俞, `koo` 顾/古, plus bicultural `shin`/`son`/`soo`/`suh`); the per-spelling measured rationale lives in the generator. `jang` in particular would otherwise be trimmed but is kept full share because the `{im, jang, jung}` trio flips the borderline eval case "Li Zheng" via a global surname-rank shift, and `koo` because trimming it rejects "Koo Ming"; the parser eval must hold at its 16-name baseline.
  - The scoring hook reads `spelling` and `target_share` and (via initialization) loads each row's `surname_ppm_as_written` into the runtime surname frequency table, so full-share rows carry the target's mass and penalty CANTONESE keys carry the discounted mass. Corpus-derived estimates (e.g. ORCID with affiliation country) can replace the numbers without a schema change.
### Corpus-Derived Name Assets: Coverage, Provenance and Refresh

Four assets are lookup tables built from Semantic Scholar author names:

| asset | built by | snapshot | fires only when |
|---|---|---|---|
| `compound_surnames.csv.gz` | `scripts/build_compound_surnames.py` ([COMPOUND_SURNAMES.md](COMPOUND_SURNAMES.md)) | October 2026 | the multi-word surname is listed |
| `two_token_order_prior.csv.gz` | `scripts/build_order_prior_asset.py` | May 2026 | the pair has >= 100 mentions and a >= 80% majority |
| `token_role_prior.csv.gz` | `scripts/build_token_order_prior.py` | May 2026 | the token has >= 200 mentions and is >= 90% one role |
| `surname_first_words.csv.gz` | `scripts/build_surname_first_words.py` | October 2026 | the word was seen in that shape and is mostly a surname (>= 3 mentions) |

- **Unseen names.** A name a table does not list gets the behavior without that rule, never a guess, so new or rare
  names are not made worse; they just do not get the gain. Shape-based rules (digraph initials, glued initials, the
  Japanese given-first veto) apply to any name.
- **Provenance.** Build every asset from source names as published, never from sinonym's output: per row, all
  `original_*` fields when `original_last` is set, else the stored fields, and never coalesce per field (the export is
  described in author-names `NAME_COUNTS.md`). An asset built from normalized names learns sinonym's own decisions.
- **Refresh.** The tables age as new authors and conventions arrive. Rebuild them from a newer snapshot periodically,
  and in particular after each ORCID backfill (more linked people strengthens the ORCID-gated compound tier), then
  rerun the ORCID ledger, the registry agreement and the S2AND gold-cluster check before shipping.
- **Measuring the gain on new names.** The held-out ORCID half guards against fitting particular people, but the tables
  were built from a snapshot that contains those names. To measure the gain on unseen names, build the tables from an
  older snapshot and score only names that first appear after it.

### Surname-First Words Before Dotted Initials
- **`surname_first_words.csv.gz`**: 40,112 words (`word, surname_first_mentions, as_last, as_first`) that sources write as `first_name` before 2-3 dotted initials (`Dmitrieva / - / N.M.`, `Назарова / - / А.Р.`) and that the corpus otherwise uses as a surname (`as_last` >= 3 and > `as_first`). The rule that consumes it (`structured_surname_first_initials_assignment`) moves the word to the surname only when it is in this list, so given names written the same way (`Sowmya / - / K. R.`) stay unchanged. Generated by `scripts/build_surname_first_words.py` from the source-name counts export.

### Chinese vs Japanese Name Classifier 
- **`chinese_japanese_classifier.skops`**: Pre-trained scikit-learn model for distinguishing Chinese from Japanese names when written in Chinese characters. At runtime `sinonym.ml_fast_scorer` reads the fitted parameters directly from this archive without importing the training stack. The training script also writes a legacy `.joblib` copy for model-development comparisons; distributions omit that runtime-unused copy.
- **`model_features.json`**: Legacy standalone feature snapshot. It is not loaded at runtime or regenerated by the training script; the authoritative vocabulary is embedded in the `.skops` model.

**Model Details:**
- **Purpose**: Classify all-Chinese character names (like "山田太郎") as Chinese vs Japanese
- **Accuracy**: 99.53% on test set of 263,409 names  
- **Training Data**: 1.3M names (1.14M Chinese, 172K Japanese from open corpora)
- **Features**: 5,000 character n-grams + 20 linguistic heuristic features
- **Algorithm**: Logistic Regression with TF-IDF character features
- **Use Case**: Fills gap where Japanese names in Chinese characters bypass romanization-based detection
- **Status**: **ACTIVE - Integrated in `sinonym.services.ethnicity.EthnicityClassificationService`**

**Model Features:**
- Character-level 1-3 gram TF-IDF features (5,000 features)
- Linguistic binary flags (20 features):
  - Japanese iteration mark (々)
  - Japanese/Chinese surname character patterns
  - Japanese/Chinese name ending patterns
  - Unique character indicators
  - Name length patterns
  - Character frequency patterns

**Training Date**: 2025-07-30

## Model Integration

The Chinese vs Japanese classifier is integrated into `sinonym.services.ethnicity.EthnicityClassificationService` and automatically activates for all-Chinese character inputs that pass initial ethnicity screening.

Runtime classification needs only NumPy and the packaged `.skops` archive. Install the `training` dependency group when retraining or running parity checks against scikit-learn:

```bash
uv sync --group training
```

## Data Generation Scripts

Scripts in the `scripts/` directory are used to generate and process these data files:
- `train_ml_classifier_for_chinese_vs_japanese.py`: Trains the Chinese vs Japanese classifier model
- `generate_surname_romanizations.py`: Regenerates `surname_romanizations.csv` from the romanization rule tables
- `generate_name_statistics.py`: Regenerates `given_position.csv` from the 120W corpus plus the byline supplement (source paths are CLI arguments)
